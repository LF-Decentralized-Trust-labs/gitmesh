|---|---|
| **Severity** | warning (5 score points; fails the run at the default `--fail-on warning`) |
| **Applies to** | `claude-code` project- and local-scope `settings`, `instructions`, `rule`, `command` and `subagent` artifacts |
| **Message shape** | four messages, one per check, below |

## What it checks

Claude Code is the one agent whose shared configuration carries permissions, hooks, imports, commands and subagents together, so it is where these contradictions can exist. Four checks, all deterministic, none sending content anywhere:

| # | Check | Message |
|---|---|---|
| 1 | **Dead allow.** The same entry appears in `permissions.allow` and in `permissions.deny` (deny wins) or `permissions.ask` (ask wins) of one settings file. Exact string match. | `"<entry>" appears in both permissions.allow and permissions.deny in <file>; deny wins, so the allow is dead - remove one side.` or `"<entry>" appears in both permissions.allow and permissions.ask in <file>; ask wins, so the allow never auto-approves - remove one side.` |
| 2 | **Allow versus hook.** An allow entry for a destructive command while a `PreToolUse` hook in the same file matches that tool (an absent, empty or `*` matcher matches every tool; only the `matcher` is read, not a handler's `if` condition). Destructive means `rm` with a flag group containing `f` (`rm -rf`, `rm -f`), `git push` with `--force` (including `--force-with-lease`; the short `-f` is not recognized), or `curl … \|`, in exact, prefix `:*` and argument forms. Hooks run regardless of allows, so the allow pre-approves exactly what the hook exists to gate. | `"<entry>" in permissions.allow pre-approves a destructive command while a PreToolUse hook matches <Tool> in <file>; hooks run regardless of allows - drop the allow or align it with the hook.` |
| 3 | **Dangling `@` import.** An instruction, rule, command or subagent body imports an `@.claude/rules/…`, `@.claude/commands/…` or `@.claude/agents/…` `.md` path that is not in the inventory. | `<file> imports @<path>, which is not in the workspace inventory; fix the path or create the file (dangling reference).` |
| 4 | **Dangling agent reference.** An instruction, rule or command body names a `subagent_type` that is neither an inventoried `.claude/agents/` subagent (frontmatter `name:`, else the file basename) nor a built-in from the July 2026 list (`general-purpose`, `statusline-setup`, `output-style-setup`, `Explore`, `Plan`). Newer built-ins such as `claude` and `claude-code-guide` are not in the list yet and are reported. Checked only when the repository defines at least one subagent. | `<file> references subagent_type "<name>", but no such agent exists under .claude/agents/ (dangling reference); fix the name or add the agent.` |

The reference checks run on unfenced lines only, so a fenced example documenting the syntax never counts. A permission entry is quoted only when nothing in it may be a credential: a secret GM001's scanner recognizes, a credential-named word (`token`, `secret`, `password`, `api_key`, `authorization`, `bearer`, `cookie`, ...), a `user:password` argument or a random-looking word. Otherwise it is shown as `Tool(…)` (`[redacted]` when the entry has no tool prefix), so a `curl -H "Authorization: Bearer …"` allow never reproduces its token in a finding.

## Why it matters

Each contradiction breaks the config's intent without granting anything by itself: a dead allow makes reviewers believe something is permitted that never is; an allow beside a gating hook hides which one wins from whoever reads the file; a dangling import or agent name fails silently at the moment a session needs it. The pattern was proven by claude-config-doctor and is generalized here.

## Example

```text
warning
  GM011  .claude/settings.json  "Bash(rm -rf:*)" in permissions.allow pre-approves a destructive command while a PreToolUse hook matches Bash in .claude/settings.json; hooks run regardless of allows - drop the allow or align it with the hook.
```

## How to fix

Remove the allow side of a dead allow and keep the deny or ask. For allow versus hook, drop the destructive allow so the hook decides each call; narrowing the hook's matcher away from the tool also clears the finding, but only by removing the gate. Fix the import path or create the file. Fix the agent name or add the agent under `.claude/agents/`.

## What it does not report

- **Other agents.** The cross-tool generalization waits on verified reference syntaxes for Codex, Cursor and the rest; inventing them would produce false findings.
- **Glob-cover analysis** across different allow and deny patterns, which would guess at Claude's matching semantics; only exact duplicates fire.
- **Nested files.** A `CLAUDE.md` inside a subdirectory (a vendored repository, a monorepo package, a test fixture) resolves imports against its own directory, which the inventory does not cover, so its references are not judged. Only root-level files and the `.claude/` trees are.
- **Imports outside the inventoried trees** (`@README.md`, `@.claude/skills/x/reference.md`): absence is not decidable there.
- **Schema validity** of hooks (event names, missing `command`) or permission rule syntax; AgentLint H1/H2 and `claude doctor` cover it.
- **Prose-level contradictions** between instructions; AgentLint's opt-in Deep mode does that with AI.
