| | |
|---|---|
| **Severity** | warning (5 score points; fails the run at the default `--fail-on warning`) |
| **Applies to** | every inventoried artifact with content, any adapter, any scope; only files that carry marker-shaped lines can fire |
| **Message shape** | names the file and line of the violation and the marker to restore |

## What it checks

A file carrying `<!-- gitmesh:managed -->` ... `<!-- /gitmesh:managed -->` markers is generated-looking by definition: `gitmesh apply` (not released yet) will rewrite only the content inside such a region and leave everything outside it alone (ADR-003). GM006 reports every way a hand edit can break that contract; a file's findings are listed by message text, not by line:

| Violation | Message |
|---|---|
| an opener inside an already-open region (regions never nest) | `Managed marker on line N of <file> opens inside the region opened on line M; managed regions cannot nest - remove one of the two openers.` |
| a closer with no open region | `Closing marker <!-- /gitmesh:managed --> on line N of <file> matches no open region; restore the opening marker or delete the stray line.` |
| a damaged marker: a full-line HTML comment naming `gitmesh:managed` that matches neither the exact opener nor the exact closer (a deleted `-->`, text after it, a marker split across lines) | `Damaged gitmesh:managed marker on line N of <file>; restore the exact single-line <!-- gitmesh:managed --> and <!-- /gitmesh:managed --> pair.` |
| a region never closed before end of file | `Managed region opened on line N of <file> is never closed; restore the <!-- /gitmesh:managed --> line so managed content can be told apart from hand edits.` |

Markers must be full-line comments; attributes are allowed on the opener. Lines inside fenced code blocks (a fence indented at most three spaces) are skipped, so a marker shown in a fenced example does not count, and an inline-code mention never matches because the line does not begin with `<!--`. A marker in an indented code block, or in a fence nested four or more spaces deep inside a list item, still counts.

## Why it matters

Until `.gitmesh/lock.json` exists, the marker pair is the only signal separating content `apply` will own from content a person wrote. Once the pair is broken, the ownership boundary cannot be drawn: a future `apply` could not tell managed content from human content in this file.

## Example

```text
warning
  GM006  AGENTS.md  Managed region opened on line 12 of AGENTS.md is never closed; restore the <!-- /gitmesh:managed --> line so managed content can be told apart from hand edits.
```

## How to fix

Restore the exact single-line pair. The previous good version is one `git log -p` away; when in doubt, put the closer back where the generated content ends. Once `gitmesh apply` ships, it will re-emit the region's content.

## What it does not report

- Files without any marker-shaped line.
- Edits *inside* a well-formed region. That is content drift, which the lockfile-based `gitmesh check` will report once it exists; this rule is the structural, pre-lockfile heuristic.

A file inventoried by several adapters (a root `AGENTS.md`) reports each violation once.
