| | |
|---|---|
| **Severity** | warning (5 score points; fails the run at the default `--fail-on warning`) |
| **Applies to** | project-scope `skill` manifests (`SKILL.md`) in every skills directory, any adapter, plus the `lockfile` artifacts that supply pins |
| **Message shape** | `Skill "<name>" has executable content but no recognized pin; pin it in .gitmesh/lock.json, skills-lock.json or .mcp.lock so what it runs is integrity-checked.` |

## What it checks

For every inventoried `SKILL.md` (`.claude/skills`, `.agents/skills`, `.agent/skills`, `.opencode/skill` and `.opencode/skills`, `.devin/skills`, `.windsurf/skills`, Antigravity plugin bundles), the rule fires when both hold:

1. **The skill has executable content.** Either the detector found script files inside the skill directory, or the `SKILL.md` body (frontmatter stripped) opens a shell code fence (`bash`, `sh`, `zsh`, `shell`, `console`) or names a script file. Bare names count for `.sh`, `.py`, `.rb`, `.ps1`, `.bash` and `.zsh` (`deploy.sh`, `run.py`), so a domain that ends in one of those suffixes (`bun.sh`, `brew.sh`, `docs.astral.sh`) counts too. `.js`, `.mjs` and `.cjs` need a path shape (`scripts/build.js`): a bare "Node.js" never fires, but a slash-joined phrase such as "React/Next.js" does.
2. **No recognized pin names the skill.** Pins are read from the keys of `skills` in `skills-lock.json` (the Vercel `skills` CLI) and the keys of `servers` in `.mcp.lock` (mcp-lock). A namespaced key (`owner/repo/name`) pins the skill its last segment names. The rule also honors the keys of `skills` in `.gitmesh/lock.json`, the lockfile `gitmesh apply` will write, but no detector inventories that file in this release, so it cannot clear the finding yet.

`.mcp.lock` records MCP servers, not skills: a server key that matches a skill's name counts as that skill's pin, and adding a skill to the file by hand breaks mcp-lock's own checksum. `skills-lock.json` is the pin to use for skills.

A skill with no shell fence, no script file and no script name never fires. Broken symlinks are skipped. A malformed lockfile contributes no pins and never aborts the run; a lockfile doctor may not read aborts it with exit `2`, like any other file.

## Why it matters

A skill whose instructions run scripts is supply chain the repository executes. A pin ties the skill to a reviewed state so a changed script is noticed before an agent runs it. Doctor does not verify hashes; it reports that nothing is recorded to verify against.

## Example

```text
warning
  GM004  .claude/skills/deploy/SKILL.md  Skill "deploy" has executable content but no recognized pin; pin it in .gitmesh/lock.json, skills-lock.json or .mcp.lock so what it runs is integrity-checked.
```

## How to fix

Pin the skill with the tool that manages it: installing a skill with the `skills` CLI records it in `skills-lock.json`, and doctor honors that pin as it is (ADR-004: reference existing pins, never duplicate them). Of the other two files the message names, `.gitmesh/lock.json` cannot clear the finding in this release and `.mcp.lock` is meant for MCP servers.

If the skill is intentionally unpinned local tooling, move its scripts out of the skill directory and remove shell fences and script file names from `SKILL.md`; the skill then counts as docs-only.

## What it does not report

- **Third-party-manager skill sources** such as `.ruler/skills/**` are inventoried as `source`, not `skill`, and never enter the rule: management is never itself a finding.
- **Skills with no executable signal**, however they were installed.
- **Content.** Whether the script is safe is a scanner's question; see [scanners](/doctor/scanners).
