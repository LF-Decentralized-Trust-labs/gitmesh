| | |
|---|---|
| **Severity** | warning (5 score points; fails the run at the default `--fail-on warning`) |
| **Applies to** | project-scope `skill` manifests (`SKILL.md`) in every skills directory, any adapter, plus the `lockfile` artifacts that supply pins |
| **Message shape** | `Skill "<name>" has executable content but no recognized pin; pin it in .gitmesh/lock.json, skills-lock.json or .mcp.lock so what it runs is integrity-checked.` |

## What it checks

For every inventoried `SKILL.md` (`.claude/skills`, `.agents/skills`, `.agent/skills`, `.opencode/skill` and `.opencode/skills`, `.devin/skills`, `.windsurf/skills`, Antigravity plugin bundles), the rule fires when both hold:

1. **The skill has executable content.** Either the detector found script files inside the skill directory, or the `SKILL.md` body (frontmatter stripped) opens a shell code fence (`bash`, `sh`, `zsh`, `shell`, `console`) or references a script file. Bare names count for unambiguous script extensions (`deploy.sh`, `run.py`, `.rb`, `.ps1`, `.bash`, `.zsh`); `.js`, `.mjs` and `.cjs` need a path shape (`scripts/build.js`), so prose like "Node.js" never fires.
2. **No recognized pin names the skill.** Pins are read from the keys of `skills` in `skills-lock.json` (the Vercel `skills` CLI), the keys of `servers` in `.mcp.lock` (mcp-lock), and the keys of `skills` in `.gitmesh/lock.json`. A namespaced key (`owner/repo/name`) pins the skill its last segment names.

Docs-only skills never fire. Broken symlinks are skipped. A malformed or unreadable lockfile contributes no pins and never aborts the run.

## Why it matters

A skill whose instructions run scripts is supply chain the repository executes. A pin ties the skill to a reviewed state so a changed script is noticed before an agent runs it. Doctor does not verify hashes; it reports that nothing is recorded to verify against.

## Example

```text
warning
  GM004  .claude/skills/deploy/SKILL.md  Skill "deploy" has executable content but no recognized pin; pin it in .gitmesh/lock.json, skills-lock.json or .mcp.lock so what it runs is integrity-checked.
```

## How to fix

Pin the skill with the tool that manages it. With the `skills` CLI, installing a skill records it in `skills-lock.json`; with mcp-lock, `.mcp.lock` records servers. Doctor honors both as they are (ADR-004: reference existing pins, never duplicate them). `.gitmesh/lock.json` is the pin `gitmesh apply` will write; no detector inventories it in this release, so it cannot clear the finding yet.

If the skill is intentionally unpinned local tooling, moving its scripts out of the skill directory and its shell examples out of `SKILL.md` makes it docs-only.

## What it does not report

- **Third-party-manager skill sources** such as `.ruler/skills/**` are inventoried as `source`, not `skill`, and never enter the rule: management is never itself a finding.
- **Skills with no executable signal**, however they were installed.
- **Content.** Whether the script is safe is a scanner's question; see [scanners](/doctor/scanners).
