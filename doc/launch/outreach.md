# Coexistence outreach: Ruler, rulesync and @agents-dev/cli

One issue to each of the three sync tools whose sources GitMesh plans to import (pivot §12 T2.5, §17.5, [ADR-004](../adr/ADR-004-coexistence.md)). Each says what doctor does with that project's files today and what the importer will read, asks a question or two, and points to our docs, which link to the project. Nothing here is published by merging it. A maintainer opens each issue by hand, from their own account, once the blocking items below are done and both maintainers have reviewed the tone.

## Before opening: blocking

Each project's maintainer will probably run doctor on their own repository first. On 2026-10-19, gitmesh-cli 0.4.0 (`@next`) misreads Ruler's and @agents-dev/cli's own repositories, and repositories those two tools manage:

- [ ] **GM010 stops warning on `AGENTS.md`-only repositories** ([#484](https://github.com/LF-Decentralized-Trust-labs/gitmesh/issues/484)). It warns on Ruler's and @agents-dev/cli's own repositories, citing a Claude Code limitation that ended with v2.1.277.
- [ ] **GM002 stops counting Cursor as present from `AGENTS.md` alone** ([#493](https://github.com/LF-Decentralized-Trust-labs/gitmesh/issues/493), [#488](https://github.com/LF-Decentralized-Trust-labs/gitmesh/issues/488)). Both repositories get a warning about a missing Cursor hook only because they have an `AGENTS.md`.
- [ ] **GM001 leaves @agents-dev/cli's `.agents/local.json` alone** ([#504](https://github.com/LF-Decentralized-Trust-labs/gitmesh/issues/504)). That tool keeps secrets there by design; today doctor reports each one as an error and says to move it out.
- [ ] **Ruler's outputs are labeled and its source is listed once** ([#505](https://github.com/LF-Decentralized-Trust-labs/gitmesh/issues/505)). Today GM010 asks Ruler users to edit the `CLAUDE.md` that Ruler generates.
- [ ] **The fixes are released** under the dist-tag the drafts link, `@next` (or `latest`, if it is promoted first).
- [ ] **Each "today" paragraph matches the release.** #504 and #505 may land differently from what they suggest; reword the drafts to say what doctor actually does.
- [ ] **Doctor re-run** on each project's default branch, with nothing wrong about that project's files. On 2026-10-19 rulesync's repository also gets a GM005 warning: its `deepwiki` server points at `/sse` in `.gemini/settings.json` and at `/mcp` in `.rulesync/mcp.json` and `opencode.json`. That is a real finding about their repository, not about their tool, so it stays out of the issue.
- [ ] **Facts re-checked** on the day, against the table below and each project's README and latest release.
- [ ] **Both maintainers signed off** in the review table.

## When

All three on the same day, a few days before Show HN. The launch posts name these tools, and their maintainers should hear about GitMesh from us first. The Show HN answer to "Isn't this what Ruler or rulesync do?" links the rulesync issue.

## Rules for these issues

- **One issue per project**, opened by a maintainer from their own account. `{name}` in each draft is whoever opens it.
- **Issues, not Discussions.** All three projects have Discussions enabled, but recent discussions there got no maintainer reply, and issues do.
- **Easy to close.** Each issue says it is not a bug report and needs no reply. A close is an answer.
- **No follow-ups.** No pings, no comments on their other issues, no pull requests nobody asked for. Answer what they write, and file anything they report about doctor as a GitMesh issue.
- **Nothing in return.** Our docs link to each project whatever its maintainer answers.
- **Promise only what exists.** Doctor ships; the importers (T3.10, T3.11) and `gitmesh policy` are planned. No dates.
- **Their format, their call.** We adapt our importers to their formats and never ask them to change theirs for us.
- The launch kit's [rules for every post](README.md#rules-for-every-post) apply as well.

## Ruler

intellectronica/ruler. Its maintainer has not commented on an outside issue since June, so expect a slow answer or none, and do not follow up.

**Title**

```text
Recognizing Ruler's files in another tool (GitMesh): two questions
```

**Body**

> Hi, I'm {name}, one of the maintainers of [GitMesh](https://github.com/LF-Decentralized-Trust-labs/gitmesh). Its `gitmesh doctor` command audits the coding-agent configuration committed to a repository, for many agents at once: read-only, no network. This isn't a bug report and needs no reply; closing it is a fine answer.
>
> **What doctor does with Ruler today.** It recognizes `.ruler/ruler.toml`, the Markdown sources under `.ruler/` and the legacy `.ruler/mcp.json`, and labels them "managed by ruler". Being managed by Ruler is never a finding, and doctor doesn't suggest edits to the files Ruler generates: their fix belongs in `.ruler/`. It still checks Ruler's config the way it checks any agent's, so a plaintext token in `ruler.toml` gets reported.
>
> **What's planned.** A `gitmesh migrate` command that reads `.ruler/` into GitMesh's own source, for people who want to move, and that we'll keep working as Ruler changes. It only reads, never writes to `.ruler/`, and needs nothing from you.
>
> **Two questions**, so we read Ruler's files the way you intend:
>
> 1. Is the `<!-- Generated by Ruler -->` banner a stable way to recognize Ruler's output? We'd use it to tell a generated root `AGENTS.md` from a hand-written one that Ruler prepends as input.
> 2. Doctor recognizes only the root `.ruler/` today. Is nested mode settled enough for us to recognize nested `.ruler/` directories too, or would you rather we wait while it's experimental?
>
> Our docs link to Ruler from [the page that lists what doctor reads](https://github.com/LF-Decentralized-Trust-labs/gitmesh/blob/main/docs/doctor/coverage-matrix.md#third-party-managers). If you ever list related tools, doctor may be useful there as a read-only check for Ruler-managed repositories; entirely up to you.
>
> Thanks for Ruler.

## rulesync

dyoshikawa/rulesync. This is the collaboration conversation pivot §15 CT2 asks for: rulesync's permissions feature already does much of what `gitmesh policy` plans to do, so the issue says so first.

**Title**

```text
Reading .rulesync/ from another tool (GitMesh), and comparing notes on permissions
```

**Body**

> Hi, I'm {name}, one of the maintainers of [GitMesh](https://github.com/LF-Decentralized-Trust-labs/gitmesh). Its `gitmesh doctor` command audits the coding-agent configuration committed to a repository, for many agents at once: read-only, no network. This isn't a bug report and needs no reply; closing it is a fine answer.
>
> **What doctor does with rulesync today.** It recognizes `rulesync.jsonc`, `rulesync.local.jsonc`, the Markdown sources under `.rulesync/`, the `mcp`, `hooks` and `permissions` files and the legacy ignore files, and labels them "managed by rulesync". Being managed is never a finding. It still checks rulesync's config the way it checks any agent's, so a plaintext token in `.rulesync/mcp.jsonc` gets reported.
>
> **Where we overlap.** GitMesh plans a `gitmesh migrate` command that reads `.rulesync/` into its own source, and later a `gitmesh policy` command that compiles one permission policy into each agent's native settings. rulesync's permissions feature already does that, for more than 40 tools, and has since April; our own planning missed it. We'd rather talk about the overlap now than after building something next to it.
>
> **Two questions:**
>
> 1. For reading `.rulesync/`, should an importer target the schemas you publish with each release (`config-schema.json`, `mcp-schema.json`, `permissions-schema.json`)? And how would you like an importer to notice a breaking change to the source format?
> 2. Would you be open to comparing notes on permissions before we build ours? For example, whether a policy GitMesh compiles could be written as `.rulesync/permissions.jsonc` instead of a second format, and how you see org-managed files such as Claude Code's managed settings or Codex's `requirements.toml`, which neither tool emits today.
>
> Our docs link to rulesync from [the page that lists what doctor reads](https://github.com/LF-Decentralized-Trust-labs/gitmesh/blob/main/docs/doctor/coverage-matrix.md#third-party-managers). If a read-only cross-tool check would help rulesync users, a mention wherever it fits is welcome; entirely up to you.
>
> Thanks for rulesync, and for documenting each tool's format as carefully as you do.
